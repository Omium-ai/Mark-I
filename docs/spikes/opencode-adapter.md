# Spike: opencode plugin/session surface — go/no-go for the opencode adapter slot

Gates: `03-hld.md` §6 opencode row, `08-api-contracts.md` §5.4, FR-AGENT-013. URLs read 2026-09-15 against `anomalyco/opencode` (npm `opencode-ai`, latest `1.18.31`, 2026-09-14). **Canonical repo/org confirmed**: [github.com/anomalyco/opencode](https://github.com/anomalyco/opencode); `sst/opencode` is the superseded old name (docs-fix PR "canonicalize sst/opencode -> anomalyco/opencode", [rodsnyder/opencode#4](https://github.com/rodsnyder/opencode/pull/4)). Site: [opencode.ai](https://opencode.ai).

## Verdict: GO-WITH-CONDITIONS — Phase 4 (as scheduled)

opencode has a real, rich event surface (25+ named bus events, including tool-gating hooks) and a stronger local usage surface than the plan's "unverified in every column" starting point — a typed per-step token/cost event plus a real SQLite session/message store; like the other three spikes, it is not hookless. Two things keep this off a clean GO. First, its extension model is an **in-process TypeScript module loaded into the opencode server**, not a subprocess fed JSON on stdin the way Claude Code/Codex/Gemini hooks work — `mark1-hookshim`'s per-invocation-subprocess design does not transplant; the adapter needs either a bundled JS plugin dialing `mark1d` over the local fabric (§4) or a tailer on the built-in `GET /event` SSE stream, and picking one needs running code, not docs. Second, the project is mid-migration to a "v2" schema (`/v2/docs`, `specs/v2/*.md` reshaping the session/message shape confirmed below) — churn beyond ordinary semver. Upside: the plan's Anthropic-OAuth risk is moot — opencode dropped bundled Claude Pro/Max OAuth client-side, and Anthropic blocked third-party subscription tokens fleet-wide — so usage capture doesn't depend on credential regime at all, since opencode normalizes usage itself before it reaches the plugin/event layer.

## Q1 — Hooks/plugin surface: real, but in-process JS, not subprocess+stdin

Plugins are async TS/JS modules — `export const P = async ({ project, client, $, directory, worktree }) => ({ ...hooks })` — loaded from `.opencode/plugins/` (project) or `~/.config/opencode/plugins/` (global), or declared in `opencode.json`'s `"plugin"` array (npm spec, pinned spec, file path, or `[name, options]` tuple); npm plugins install via Bun into `~/.cache/opencode/node_modules/` ([opencode.ai/docs/plugins](https://opencode.ai/docs/plugins)). 25+ events exist: `tool.execute.before/after`, `session.*` (created/idle/status/updated/compacted/diff/error/deleted), `message.*` (updated/removed/part.updated/part.removed), `permission.asked/replied`, `file.edited`, `lsp.*`, `tui.*`. Gating is real: `tool.execute.before` can mutate args or `throw` to block (`.../session/tools.ts`): order is `trigger("tool.execute.before") → ctx.ask(permission) → execute() → trigger("tool.execute.after")`; a thrown error skips permission-check and execution entirely. Permission is a separate declarative ruleset (`"permission": {"edit":"deny","bash":{"git *":"allow","*":"ask"}}`, actions `allow|ask|deny`, glob-matched, last-match-wins) over 15 tool keys ([/docs/agents](https://opencode.ai/docs/agents), [/docs/permissions](https://opencode.ai/docs/permissions)). No hook payload carries token usage, consistent with 08 §5 rule 4.

## Q2 — Token usage: strong, typed, but the dedupe key needs an empirical check

`session.next.step.ended` fires per LLM call (a "step" — one round-trip, which can repeat inside one user turn under tool-call loops) and carries `assistantMessageID`, `finish`, `cost`, `tokens:{input,output,reasoning,cache:{read,write}}` (`packages/schema/src/session-event.ts`; published from `.../session/runner/llm.ts`). Two capture paths need no wire access: (a) a plugin's generic `event` hook, live objects in-process; (b) the server's `GET /event` SSE stream (`opencode serve`, default `127.0.0.1:<ephemeral>`), envelope `{id, type, properties}` ([opencode.ai/docs/server](https://opencode.ai/docs/server)). Caveat: `assistantMessageID` is created once per message and **reused across multiple step events for the same message** in a tool-loop turn (`publish-llm-event.ts`), so alone it is not a safe FR-SPINE-003 dedupe key — a composite with the SSE envelope's `id` (or a step ordinal) is the likely fix, but reconnect-stability was **not found in source as of 2026-09-15**. Session-level cumulative totals persist in SQLite (`cost`, `tokens_input/output/reasoning/cache_read/cache_write`, `.../session/sql.ts`). Notable: `packages/llm/DESIGN.md` documents a provider-normalized `GenerateResult.usage`/`cost` shape opencode computes itself — usage capture is credential-regime-agnostic by construction, unlike Claude Code, where subscription usage needs a transcript tail because there is no other source. **OTel note (flagged per gate policy):** opencode ships a real OpenTelemetry OTLP exporter (`.../observability/otlp.ts`, config flag `openTelemetry`, env `OTEL_EXPORTER_OTLP_ENDPOINT/_HEADERS`) — a remote push exporter, off by default, needing an external collector; not a local file, no OTel dependency taken, irrelevant to this adapter's design.

## Q3 — Provider/credential model: BYOK, proxyable base URL, Anthropic-OAuth is dead

Any provider's endpoint is overridable — `provider.<id>.options.baseURL` in `opencode.json` — a general Vercel-AI-SDK mechanism, not Anthropic-specific ([opencode.ai/docs/providers](https://opencode.ai/docs/providers)); structurally the same shape as `ANTHROPIC_BASE_URL`. `opencode auth login` and `client.auth.set({path:{id}, body:{type:"api", key}})` write to `auth.json`. On OAuth/subscription: opencode's docs say "Previous versions of OpenCode came bundled with these plugins [for Claude Pro/Max] but that is no longer the case as of 1.3.0" because "Anthropic explicitly prohibits this," naming ChatGPT Plus/Copilot/GitLab Duo as still usable "with zero setup" (same URL). Third-party reporting (not opencode's docs) — [HN #46625918](https://news.ycombinator.com/item?id=46625918), [dev.to](https://dev.to/mcrolly/anthropic-kills-claude-subscription-access-for-third-party-tools-like-openclaw-what-it-means-for-3ipc) — describes Anthropic blocking third-party Pro/Max OAuth fleet-wide around 2026-04-04, after a Jan 2026 spoofing-detection tightening. Net: no live Anthropic subscription regime to guard against; a generic `POST /provider/{id}/oauth/authorize` route exists for other providers but was not probed further.

## Q4 — Persistence: SQLite (Drizzle), `~/.local/share/opencode/`

`opencode db path` prints the DB file; `opencode db [query]` opens an interactive `sqlite3` shell or runs raw SQL. Tables: `session` (cumulative cost/tokens, `model{providerID,modelID,variant}`, `permission` snapshot), `message` (`id` PK, `session_id` FK cascade, `data` JSON blob typed `V1MessageData`), `part` (per-message content, cascades from `message`) — `.../session/sql.ts`. Docs also describe `~/.local/share/opencode/project/<slug>/storage/` (or `.../global/storage/` outside a git repo) for "session and message data" plus `auth.json` for credentials ([/docs/troubleshooting](https://opencode.ai/docs/troubleshooting)); the relationship between that directory and the SQLite file was **not fully resolved from docs alone** — first thing to check empirically. The exact on-disk V1 `Assistant` message schema (per-message usage, distinct from the session rollup) was likewise **not found verbatim**; a `specs/v2/message-shape.md` proposal shows `Assistant{usage:{cost,tokens}}` as a *cleanup* of current storage, implying today's V1 shape carries something equivalent, unconfirmed byte-for-byte.

## Q5 — Versioning and churn

npm `opencode-ai`, latest `1.18.31` (2026-09-14) — pin via `npm install opencode-ai@<exact>`. Last 10 GitHub releases ([anomalyco/opencode/releases](https://github.com/anomalyco/opencode/releases)): v1.18.22 (08-24) → .23 (08-25) → .24/.25 (08-28, same day) → .26 (09-01) → .27 (09-02) → .28/.29 (09-04, same day) → .30 (09-09) → .31 (09-14) — roughly one release every 2 days, two same-day hotfix pairs in three weeks; fast, though not Codex-alpha-channel fast. The larger risk is structural, not cadence: an active v1→v2 schema migration (live `/v2/docs`, `specs/v2/*.md` for session, message shape, provider/model) means the V1 shapes confirmed here already have a visible successor in design.

## What the adapter slot needs

- **In-process plugin (capture + gate):** viable, richer than a subprocess hookshim, but a new artifact class — not a reuse of `mark1-hookshim`.
- **SSE tail (`GET /event`):** hookshim-free usage alternative; needs ephemeral-port discovery outside the in-process `event` callback.
- **Transcript/DB tail:** viable for backfill and cumulative totals; per-message granularity and the storage-dir-vs-SQLite relationship need inspecting on a real install first.
- **Proxy (API-key regime):** viable via `provider.<id>.options.baseURL`, reusing `mark1-frames` dialect parsers; no opencode-specific wire work implied.
- **Net:** unlike Codex, Usage needs no choice between file tail and live stream — both exist, typed, agreeing on fields; the open question is dedupe-key composition and plugin-vs-SSE cost, not availability.

## Open risks

1. `assistantMessageID` reuse across steps makes the FR-SPINE-003 dedupe key a composite, unconfirmed-stable — verify against a running session before ingest wiring.
2. The in-process plugin model is a scope change from the subprocess-hookshim design of the first three adapters — budget a new capture mechanism, not a port.
3. Active v1→v2 schema migration risks invalidating a pinned conformance fixture faster than ordinary version churn.
4. The SQLite-file vs. `project/<slug>/storage/` relationship, and literal on-disk V1 Assistant-message usage fields, are unconfirmed — first things to check empirically.
5. Non-Anthropic subscriptions (ChatGPT Plus, Copilot, GitLab Duo) work "with zero setup"; their credential/usage-visibility mechanics were not investigated.
