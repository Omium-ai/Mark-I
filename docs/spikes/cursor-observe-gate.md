# Spike: Cursor hooks, usage visibility, and BYOK routing

**Scope:** Gates the Phase 5 `cursor` observe/gate slot per `docs/08-api-contracts.md` §5.6 and the Cursor row of `docs/03-hld.md` §6's capability matrix. Read against FR-AGENT-015 (`docs/02-requirements.md`). All facts read 2026-09-15.

## Verdict: GO-WITH-CONDITIONS — stays Phase 5 observe/gate; proxy is NO-GO in every regime, not just subscription

Hooks are real, shipped since Cursor 1.7 (2025-09-29, "in beta"; no later GA entry found), close enough to Claude Code's/Copilot's vocabulary that field-mapping is bundle data, not new plumbing. Two findings change the plan's assumptions rather than fill them in. First, the CLI (`cursor-agent`) — the surface an enterprise deployment would most plausibly target — has documented-but-user-reported-broken coverage of exactly the hook Mark 1 needs most (`stop`), so the slot needs a live fixture proving CLI parity, not IDE parity alone. Second, more consequential: **BYOK is never proxy-eligible for Cursor, in any regime.** Cursor's own docs state a customer's own API key does not make the client call the provider directly — every request, BYOK or not, transits Cursor's backend for "final prompt building." This refutes FR-AGENT-015's "BYOK where Cursor exposes it: proxy eligible per provenance" clause: no provenance state makes Cursor's wire interceptable, because the client speaks to Cursor, never the provider. Recommendation: keep the slot Phase 5 observe/gate as scoped; close wire-proxy and model-rewrite to a permanent NO-GO rather than "unverified."

## Q1 — Hooks

Real, documented at [cursor.com/docs/hooks](https://cursor.com/docs/hooks) (read 2026-09-15). Introduced in Cursor 1.7 (2025-09-29), "currently in beta" per the release notes ([cursor.com/changelog/1-7](https://cursor.com/changelog/1-7), read 2026-09-15); no later entry found dropping the beta label. Agent-scoped events: `sessionStart`/`sessionEnd`, `preToolUse`/`postToolUse`/`postToolUseFailure`, `subagentStart`/`subagentStop`, `beforeShellExecution`/`afterShellExecution`, `beforeMCPExecution`/`afterMCPExecution`, `beforeReadFile`/`afterFileEdit`, `beforeSubmitPrompt`, `preCompact`, `stop`, `afterAgentResponse`/`afterAgentThought`; plus Tab's `beforeTabFileRead`/`afterTabFileEdit` and `workspaceOpen`. Config: `~/.cursor/hooks.json` (user), `<project>/.cursor/hooks.json`, `/etc/cursor/hooks.json` (enterprise), team via dashboard, all layers additive (GitButler, [blog.gitbutler.com/cursor-hooks-deep-dive](https://blog.gitbutler.com/cursor-hooks-deep-dive), read 2026-09-15, cross-checked against the vendor schema). Gating: exit 0 + JSON is normal; exit 2 = deny; other non-zero = fail-open by default, reversible via `failClosed: true`; permission merges as `deny` > `ask` > `allow`. `stop`'s only output is `followup_message`, auto-submitting a new turn — the same mechanism as Claude Code's `Stop` (`decision:"block"` forces continuation), different field name, same shape — **if the event fires**.

Scope: confirmed for IDE Agent Chat/Cmd+K and cloud agents (a defined subset — no `sessionStart`/`sessionEnd`, MCP, or Tab hooks there). For the CLI: the changelog claims comprehensive support added January 2026 ("stop hooks with follow-up loops... subagent lifecycle hooks") and richer per-turn fields in March 2026 ([cursor.com/docs/cli/changelog](https://cursor.com/docs/cli/changelog), read 2026-09-15) — but a forum thread from the same window reports `stop`, `beforeSubmitPrompt`, `afterAgentResponse`, `afterAgentThought`, and `beforeReadFile` as non-functional in the CLI, one respondent stating "the source code in your product simply discards it" ([forum.cursor.com/t/cursor-cli-hooks/148511](https://forum.cursor.com/t/cursor-cli-hooks/148511), read 2026-09-15). **Not found as of 2026-09-15:** vendor confirmation this gap closed, or whether Composer (Cursor 2.0's panel/model) fires hooks independently of Agent Chat.

## Q2 — Usage visibility

No billing-grade per-request token count exists locally in the IDE: `state.vscdb` (`~/.config/Cursor/User/globalStorage/` on Linux) carries a `tokenCount` on chat bubbles, but it reflects context-window occupancy, not billed usage, and third-party tooling built against it (`codeburn`) reports it returning zero despite a populated database — a confirmed dead end. The CLI differs: `--output-format stream-json` carries per-turn `inputTokens`/`outputTokens`/`cacheReadTokens`/`cacheWriteTokens` plus a `request_id` since 2026-02, and `stop`/`afterAgentResponse` hook payloads gained the same fields plus a stable `generation_id` present on every hook payload ("changes with every user message") since 2026-03 ([forum.cursor.com/t/how-to-obtain-token-usage-per-request/168317](https://forum.cursor.com/t/how-to-obtain-token-usage-per-request/168317), read 2026-09-15). This would be a genuine exception to the estate's "no hook payload carries token usage" rule (08 §5 rule 4) — but it's CLI-only, per-turn, parent-agent-only, and sits on the same events §Q1 reports as broken, so it can't be trusted without a live fixture. Otherwise, authoritative usage lives only in Cursor's dashboard/Admin API (`POST /api/dashboard/get-filtered-usage-events`).

## Q3 — Regimes and BYOK routing

Subscription tiers (Pro/Pro Plus/Ultra) meter two usage pools against a monthly reset; usage-based pricing adds on-demand spend past quota, surfaced only via the dashboard or CLI `/usage`, never per-request locally. BYOK supports OpenAI, Anthropic, Google, Azure OpenAI, and AWS Bedrock ([cursor.com/help/models-and-usage/api-keys](https://cursor.com/help/models-and-usage/api-keys), read 2026-09-15), with an "Override OpenAI Base URL" setting. **None of this is proxy-eligible.** "Even if you use your API key, your requests will still go through our backend! That's where we do our final prompt building." ([cursor.com/data-use](https://cursor.com/data-use), read 2026-09-15). This is unlike Claude Code/Codex/Gemini CLI, where the vendor client itself is the HTTP caller to the provider and a base-URL env var redirects that call to our proxy. Cursor's client calls Cursor's backend; the backend calls the provider (or the overridden URL) server-side. No customer-machine vantage point sees that second hop — the provenance guard in FR-AGENT-015 has nothing to gate, because no credential state changes where the client sends bytes.

## Q4 — Enterprise telemetry export

Confirmed: "Cursor pushes to your collector over OTLP/HTTP binary protobuf. gRPC and JSON are not supported" ([cursor.com/docs/enterprise/opentelemetry-export](https://cursor.com/docs/enterprise/opentelemetry-export), read 2026-09-15). Server-side, customer-owned infra — the org admin points Cursor's backend at their own collector; metrics (`cursor.token.usage`, `cursor.tool.calls`, `cursor.cost.usage`) are at-most-once, logs at-least-once, deduped on `cursor.event.id`. This is Cursor's export contract into infrastructure the customer runs, never an OTel dependency Mark 1 would add — if a tenant runs that collector, `mark1d` could read the sink as a DIAGNOSTIC source, same posture as Gemini CLI's telemetry outfile (`docs/spikes/gemini-cli-beforemodel-oauth.md` §2). ADR-0005 (no OTel in M1P) is unaffected.

## Q5 — Version churn

Hooks: Cursor 1.7 (2025-09-29) → present, ~11.5 months, still beta-labeled at launch with no confirmed GA entry since. IDE major releases run roughly weekly to biweekly (1.7 → 2.0 → 3.0 → "Cursor Projects" on 2026-09-10). The CLI has its own cadence, with hook-relevant changes in at least four of the trailing nine months (Jan, Feb, Mar, Jul 2026). No stated deprecation or stability policy for hooks was found. Pin exact IDE + CLI build numbers for the fixture; re-run more often than the plan's "major vendor release" default, matching Copilot's precedent.

## What the adapter slot needs

- **Capture: hooks** — viable for IDE Agent Chat/Cmd+K now; CLI parity unverified and contested — fixture must exercise both surfaces, not assume IDE behavior extends to CLI.
- **Capture: transcript/usage** — no billing-grade local IDE source; CLI `stream-json`/hook per-turn fields are the only candidate, DIAGNOSTIC-class until the fixture confirms they populate and aren't the discarded fields of §Q1.
- **Injection: stop/tool gates** — `stop`'s `followup_message` maps onto Mark 1's force-continue pattern; `before*` hooks give `preToolUse`-equivalent gating via `permission: "deny"`.
- **Injection: context/MCP** — `sessionStart.env`/`additional_context` and `beforeSubmitPrompt` are viable map-delivery points, same shape as every other adapter.
- **Wire proxy / model rewrite** — **NO-GO, permanently**: Cursor's docs foreclose a direct client→provider hop in every regime, so this column should close rather than stay pending.

## Open risks

1. CLI hook reliability (`stop` especially) is vendor-claimed-working vs. user-reported-broken in the same month — one live `cursor-agent` session is required before trusting any fixture.
2. No confirmed hooks GA date — still nominally under a beta label from 2025-09-29.
3. Whether Composer (panel or model) fires hooks independently of Agent Chat is unconfirmed.
4. CLI per-turn usage fields are absent from Cursor's primary CLI docs (`cursor.com/docs/cli/using`) — sourced only from changelog prose and a forum thread; treat as provisional until a fixture captures a real payload.
